# SESSION_STATE.md

## Context Snapshot
- **Project:** Swiftorrent
- **Current Architecture:** Package-first modular Swift Package with Core, Domain, Features, and a thin SwiftUI app executable.
- **Swift Version:** 6.3.2
- **Next Immediate Step:** R4 (MSE/PE outbound encryption) is **DONE + live-validated** this session — see top of Recent Fixes. Every peer connection now attempts the MSE handshake (DH over the fixed 768-bit group + RC4 stream) and falls back to plaintext only if the peer isn't MSE-capable, so we now reach the encryption-required majority that used to accept our TCP connection then go silent. Live run: 13 peers connected, **12 negotiated RC4, 11 downloaded + SHA-1-verified real pieces**. **Highest-value remaining work:** magnet-path PEX during the info-hash→metadata exchange (PEX + MSE already cover the swarm download; only the metadata step is still trackers + DHT). After that: harden best-effort delete for unresolved rows, or migrate to a native Xcode app target. Live smoke test uses `big-buck-bunny.torrent` and the Big Buck Bunny magnet in the repo root / README. NOTE: avoid rapid repeated live magnet runs — hammering shared trackers/peers appears to transiently throttle the source IP.

## Modules & Targets
- **App:** `SwiftorrentApp` in `App/Sources/SwiftorrentApp`
- **Core:** `SwiftorrentCore` for bencode, metainfo, magnet parsing, magnet metadata resolution, trackers, peer-wire, and downloading. The download stack is split one-responsibility-per-file: `TorrentDownloader` (thin orchestrator), `WebSeedDownloader` (HTTP/BEP-19), `PeerSwarmDownloader` (peer-wire pool), `PieceDownloadCoordinator` (rarest-first scheduling/accounting actor), `TorrentFileWriter` (disk I/O + verify/finalize), `FileProgressMapper`, `TorrentDownloadProgress`/`TorrentFileProgress` (progress types), and `RateLimiter` (shared token-bucket throughput cap).

- **Features:** `SwiftorrentFeatures` for SwiftUI root UI.
- **Tests:** `SwiftorrentCoreTests` and `SwiftorrentDomainTests`, both using Swift Testing.

  - Feature (MSE/PE outbound encryption, R4 — DONE + LIVE-VALIDATED): `PeerWireClient` now attempts the MSE/PE (BEP-8 Message Stream Encryption) handshake as the initiator before every connection, falling back to plaintext only if the peer isn't MSE-capable. New `MSECrypto.swift` (Core) provides the two primitives Apple's frameworks lack: (1) Diffie-Hellman over MSE's fixed 768-bit prime (`G=2`) via a small pure-Swift fixed-width big integer (`BigUInt`, `[UInt32]` little-endian limbs, right-to-left square-and-multiply; the `mod` hot loop uses `withUnsafeMutableBufferPointer` so a modexp is ~4 ms in Release), and (2) RC4 (`process`/`discard`). SHA-1 = CryptoKit `Insecure.SHA1`. Handshake flow in `PeerWireClient.mseHandshake()`: send Ya‖PadA → read Yb → derive `S` + keyA/keyB ciphers (`MSE.outgoingCipher`/`incomingCipher`, each discarding 1024 keystream bytes) → send `HASH('req1',S) ‖ HASH('req2',SKEY)⊕HASH('req3',S) ‖ ENCRYPT(VC‖crypto_provide‖0‖0)` with `crypto_provide = 0x02` (RC4 only, so a completed handshake is always encrypted) → `readCryptoSelect` resyncs on the peer's encrypted VC (scans past PadB, bounded by `maxResyncBytes`), decrypts `crypto_select`+PadD, and installs `sendCipher`/`recvCipher`. All wire I/O then flows through those RC4 states transparently: `send` encrypts, and receives now drain a raw `inputBuffer` (needed so the VC resync can over-read) then decrypt via `recvCipher`. New `connect()` structure: `openConnection()` (TCP ready dance) → policy switch (`EncryptionPolicy.preferEncrypted` default / `.plaintextOnly`); on MSE failure it `close()`s, `resetForReconnect()`s, and retries plaintext on a fresh socket. - **MSE/PE outbound encryption is DONE (R4).** `PeerWireClient` attempts the MSE handshake before every connection (`.preferEncrypted` default) and falls back to plaintext for non-MSE peers, so the encryption-required peers that used to accept our TCP connection then go silent are now usable. Adding a listener would break the download-only posture and is intentionally NOT planned. Avoid rapid repeated live magnet runs while testing — hammering shared trackers/peers appears to transiently throttle the source IP.
- Magnet metadata resolution (`MagnetMetadataResolver`) is concurrent + reachability-aware: `collectPeers` returns on `enoughPeersToStart = 300` or an 18s deadline (whichever first, then cancels stragglers) so a slow DHT no longer stalls the "Contacting…" stage; the fetch phase runs `maxConcurrentMetadataFetches = 24` workers over a `PeerCursor` actor (broad first pass over up to `maxMetadataPeers = 300`, then retries only peers that connected via `markReachable`), first SHA-1-verified metadata wins, bounded by `metadataPhaseDeadline = 90s`. `PeerWireClient.readUntilMetadataHandshake` stops at the peer's extension handshake (`receivedExtendedHandshake`) so a reachable leecher is dropped in ~1 RTT. `connectTimeout` for metadata probes = 8s.
- Peer discovery uses HTTP/HTTPS trackers, UDP trackers, DHT, and **inbound PEX (BEP 11)** during swarm download. PEX lives in `PeerWireClient`, so it serves both `.torrent` and magnet swarm downloads (both flow through `PeerWireClient`/`PeerSwarmDownloader`); PEX peers are deduped into the `PeerSupply` reserve for pool replenishment. Download-only: we declare `ut_pex` to *receive* gossiped peers but never advertise an `added` list. Magnet *metadata* exchange (info-hash → metadata) still uses trackers + DHT only (adding PEX there is the remaining Roadmap "reach more peers" item).
- **Every peer connection is encrypted-first (MSE/PE, R4):** `PeerWireClient.connect` tries the MSE handshake and installs RC4 send/recv ciphers, falling back to plaintext on a fresh socket for non-MSE peers. Covers both `.torrent` and magnet swarm downloads (shared peer-wire layer). Crypto in `MSECrypto.swift`; `isEncrypted` reports the negotiated transport. Metadata-exchange connections (`MagnetMetadataResolver`) also go through `PeerWireClient`, so they are encrypted-first too.
- Downloader uses a self-replenishing concurrent peer pool (4 workers over a shared `PeerSupply` reserve; dead peers are replaced from the ~24-peer reserve) with per-wait peer-wire timeouts. Live-validated against `big-buck-bunny.torrent` (repo root).
- Disk deletion removes known torrent output paths and partial `.tor` files; unresolved/queued rows (no `outputRelativePaths`) skip disk deletion entirely (logged) rather than guessing from the item name. Swallowed file-delete/persistence failures are logged via `os.Logger` (subsystem `Swiftorrent`).
- File selection is chosen up front in the add dialog. After a download starts, the row's expandable file list no longer toggles selection; instead its per-file trash button deletes a file from disk and `deleteFile` deselects it, cancelling/restarting a live download (re-verifies on-disk pieces) so the scheduler drops it. Partial selections download via web seeds (selected files whole + range-fetched neighbor slices of shared boundary pieces) and via peers. Deselected files that received shared-boundary bytes are cleaned up at finalize.
- The torrent list now persists across launches (`session.json` under Application Support) and downloading rows auto-resume. Persistence stores the `info` dict per item to rebuild the metainfo offline; if a stored `info` dict ever fails to parse, that row is silently dropped on restore rather than shown broken.
- Download throughput can be capped via a shared `RateLimiter` token bucket. Limiting is applied *after* each chunk/piece is read (it throttles by pausing the read loop), so the cap governs the running average rather than instantaneous burst; a peer piece larger than one second's budget is admitted after a proportional wait.
- Manual app bundling is required because the current project is an SPM executable instead of a native Xcode app target.
- The Big Buck Bunny magnet link (documented in README) drives magnet-path testing (info-hash → metadata exchange → swarm). New test assets live in the repo root, not an external directory.

## Decisions & Rationale
- **Pure Swift/Apple-only:** Uses SwiftUI, Observation, Foundation, Network, CryptoKit, AppKit, and UniformTypeIdentifiers only.
- **Download-only:** No peer listener, tracker port is `0`, uploaded is always `0`, no block upload handling, and completion sends stopped announce. MSE/PE encryption (R4) changes only the outbound transport — no seeding is introduced.
- **MSE/PE is pure Swift:** CryptoKit has no custom-group Diffie-Hellman, so `MSECrypto.swift` implements DH over MSE's fixed 768-bit prime with a minimal `BigUInt` modexp plus RC4; SHA-1 (`HASH`) uses CryptoKit. `crypto_provide` advertises RC4 only, so any completed MSE handshake yields an encrypted stream; plaintext-only peers are handled by the fresh-socket fallback.
- **Default downloads location:** Uses the system `.downloadsDirectory` URL so localized user folders work correctly.
- **Transmission reference:** Transmission was consulted for protocol concepts only; no code was copied or translated.
